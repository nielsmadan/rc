# iTerm2

`iterm2/` holds a dynamic profile (symlinked into `~/Library/Application Support/iTerm2/DynamicProfiles/`), a colorscheme (`rc.itermcolors`, imported manually inside iTerm2), and `SaveWindowArrangement.py`.

`SaveWindowArrangement.py` is symlinked into iTerm2's `Scripts/AutoLaunch/` dir, so it runs as a long-lived daemon at iTerm2 startup. It does two things: (1) registers the `save_window_arrangement` RPC, bound to **Cmd+S** via a key mapping in `dynamic-profile.json` (action `60` = "Invoke Script Function") — on an untitled window it prompts for a name, sets that as the window title, then saves; (2) auto-saves any window that has a title set, re-saving its named arrangement (name = the title) on a debounce whenever it changes. A window is "known"/auto-saved **iff it has an iTerm2 window title** — the same titles used for Hammerspoon `WINDOW_RULES`. Untitled windows are ignored. Changing the RPC name or the Cmd+S binding means editing both the script and `dynamic-profile.json` in lockstep. Like `CloneRepoToTab.py`, its RPC body is **fire-and-forget** — the save runs as an `asyncio` task so the RPC returns immediately. Measured: iTerm2 fails an outstanding call after **5s**, and the untitled-window path awaits a text-input alert, so awaiting the save inline made every first-save of a new window report `FAILED: Timeout` — while the save itself still completed. Don't collapse it back to an inline `await`; the task reference is held in a per-window dictionary because `asyncio.create_task` keeps only a weak one.

**Both AutoLaunch daemons are loaded once, at iTerm2 startup.** Editing `SaveWindowArrangement.py` or `CloneRepoToTab.py` does not change live behaviour — the running copy keeps serving the old code until iTerm2 is restarted (or the script is re-run from iTerm2's Scripts menu). It is very easy to "fix" something and then watch the old bug reproduce.

## Agent sessions in arrangements

The saver remembers the last local Claude or Codex conversation assigned to each pane. Opening the named arrangement resumes that exact conversation in its recorded directory. Exit status 0 or 130 is treated as an intentional exit and clears only a conversation captured from that launch. This is a heuristic: a host that handles a window-close signal and returns 0 can also clear its binding. Other statuses and temporary loss of HooklineSinker presence retain recovery. Forgetting takes effect in the named arrangement after a successful save; older arrangements or copies remain independent. Failed automatic saves stay pending and retry with backoff capped at 30 seconds; failures are reported in the script log. A new conversation replaces the previous binding. It resumes conversation history, not an interrupted tool operation. Remote SSH/tmux panes retain their existing startup behavior.

Launch mode comes from the `~/ac/.airc.d/` wrappers: `claude`, `claude-raw`, `clor`, `codex`, and `codex-raw`. Each launch has a unique token. Start/end updates share a per-pane lock, and completion outcomes are retained by token under `~/.local/state/iterm-agent-resume/outcomes/`, so a later launch cannot overwrite an earlier outcome. A successful help/version command cannot forget a conversation captured from another launch. The wrapper registers its recipe, working directory, and launching-shell PID/start time through `~/ac/bin/iterm-agent-register`. These records live in the private `~/.local/state/iterm-agent-resume/launches/` directory; the saver verifies process ancestry and start time, excludes processes already present when the launch registered, and rechecks the launch record around observation. Saved bindings include the matching launch token. Nested and non-terminal invocations skip registration. Terminal escape sequences cannot select a launch recipe. No credentials, arbitrary command arguments, or process environments are recorded. Resume uses the named wrapper's current configuration and defaults; custom per-invocation flags are not replayed. A forced-sandbox preference is retained.

Sessions started before the updated wrappers were loaded have an unknown launch mode. Their identity is saved, but reopening displays an explanation and leaves a shell. Exit and resume them once through an updated wrapper (`source ~/.airc` in the shell first) to enable automatic launch. This avoids guessing whether a Claude conversation used the normal provider or `clor`.

- `iterm-agent-resume --clear` forgets this pane's conversation and disables capture for the current live pane. The next save records an ordinary shell; a newly restored shell can capture agents again. Run it at the shell prompt after leaving the agent.
- `iterm-agent-resume --enable` allows capture again when an agent is running in the pane.
- Missing directories, unknown launch modes, unavailable presence, and duplicate restores leave a shell with a diagnostic. A per-conversation OS lock lasts for the launched process; an additional presence check covers agents already running elsewhere. Arbitrary manual launches outside the helper cannot participate atomically in that lock.
- One live window owns each arrangement name. Rename a second window before saving it under a different name; it cannot overwrite the first window's arrangement.

`arrangement_agents.py` contains validation, command encoding, presence matching, and locking. `arrangement_iterm.py` reconciles bindings every two seconds and before saves. It uses HooklineSinker's public `sessions --json` interface; unrelated sink-delivery failures do not invalidate presence. Session IDs are matched by UUID rather than iTerm2's positional prefix.

The resume record is versioned, machine-signed data embedded in the saved pane's startup command. Saves temporarily replace `Command`/`Custom Command` inside an iTerm2 transaction, save the arrangement, then restore the original settings. The record includes those original settings so both a newly restored pane and an interrupted save can be repaired. Live sticky bindings use `user.rcAgentResume`; named arrangements carry their own encoded copy. The helper repairs its pane before starting the agent. Daemon reconciliation also repairs leftover overrides after reconnection/restart. Unknown versions and invalid signatures are rejected without rewriting the profile. Live records are bound to their pane UUID to reject cross-pane replay. The signing key and launch records have mode 0600 inside a mode-0700 state directory, outside the agent sandbox profiles. Keep that key while arrangements use it; losing it requires clearing and saving those bindings again.

Ordinary named-arrangement restoration was verified on iTerm2 3.7.6: save → restore → split → resave → restore uses the saved profile command. App-state restoration may instead reconnect surviving jobs and must not trigger a separate launch. Keep process-launch logic in the saved command, not in a new-window watcher.

Install the helper with `./install.sh`. Stop the old saver in iTerm2's Script Console, then run it once from Scripts → AutoLaunch → SaveWindowArrangement. The new saver holds a single-instance lock; an additional launch exits. Existing open windows are reconciled on startup. To remove this feature, clear bindings and save each affected arrangement while the helper is still installed, then remove it. A saved command also falls back to a shell if its helper/runtime has disappeared. To recover a damaged saved pane manually, select its normal profile in Edit Session and save the arrangement again.

Checks: `python3 iterm2/test_arrangement_agents.py`, `python3 ~/ac/bin/test_iterm_agent.py`, and `python3 -m py_compile iterm2/SaveWindowArrangement.py iterm2/arrangement_iterm.py bin/iterm-agent-resume`. The first suite exercises orchestration with an injected iTerm API and real process locks. For live QA, use a uniquely named disposable arrangement: launch a fresh conversation and save it, then terminate only the disposable agent with a recovery-preserving status (such as SIGKILL), close its pane, reopen, and verify its exact ID via HooklineSinker. Split and resave, then open twice to check duplicate prevention. Separately test normal exit and Ctrl+C: wait for the ordinary-shell arrangement to be successfully saved before closing/reopening, and verify no agent launches. After a recovery-preserving exit, run a help/version command and verify that recovery remains. Test rapid launch replacement and a failed save followed by recovery without another UI event. Finally clear and resave. Also verify interrupted-profile recovery with presence unavailable and missing-directory/helper shell fallbacks. Close only the disposable windows and delete the test arrangement in Settings → Arrangements.

## Other iTerm2 behavior

The daemons require iTerm2's bundled Python API at runtime. `test_arrangement_agents.py` injects a fake API to cover capture, save/repair, ownership, and scheduling, alongside pure validation and real process-lock tests. `python3 iterm2/test_clone_repo_lib.py` covers the clone helper. These suites run manually; live arrangement round trips verify the real API integration.

`CloneRepoToTab.py` is the second AutoLaunch daemon (same lifecycle as `SaveWindowArrangement.py`). It registers the `clone_repo_to_tab` RPC, bound to **Cmd+Ctrl+N** in `dynamic-profile.json`. On trigger it resolves the active session's git repo, then scans the **current window's** tabs for that repo's family of sibling checkouts **open** in it (siblings = same parent dir + same base name with trailing digits stripped) and auto-picks the target by **filling the lowest gap** in the family (`select_sibling_slot`). Each open sibling occupies a *slot* = its trailing number, but a **bare name** (no digit suffix) counts as **slot 1** — the first checkout is "the first" whether it's named `foo` or `foo1`. The target is the smallest slot ≥ 1 that's unoccupied, named `base + slot`: with a hole like `foo1, foo3, foo4` it fills `foo2`; with `foo2, foo3` (no `foo1`) it fills `foo1`; a contiguous run like `foo`/`foo1` + `foo2` + `foo3` has no gap so it goes to `foo4` (the old highest-slot + 1 behaviour). Gap-filling is the point of the current design — reuse the holes left by closed checkouts instead of letting the numbers drift upward forever; don't simplify it back to highest + 1. Selection is **deterministic** — independent of which sibling triggered it. The active tab's title has no part in repo selection; it is read only after the new tab is created and supplies that tab's display-name base with the selected repo slot (`core2` + slot 3 → `core3`), falling back to the destination folder name when the active tab has no explicit title. It then shows an **OK/Cancel** confirmation. **If that sibling directory already exists** on disk, the dialog offers to open a new tab there and update it from its configured upstream; on OK it opens the tab pointed at the existing directory (splits recreated, every pane in that directory), sends `git fetch --no-write-fetch-head && git rebase --fork-point '@{upstream}'` into the main pane, then runs `lefthook check-install || lefthook install` when a Lefthook config exists — nothing is cloned, trusted, or copied, and a dirty tree or conflict surfaces as git's own error in the pane. Avoiding `FETCH_HEAD` prevents this command from racing Pure's asynchronous prompt fetch. **Otherwise** the dialog offers to clone `<origin>` into the new sibling; on OK it creates the empty directory, opens the new tab (same split structure), then sends a shell command into the main pane that runs `git clone <origin> .`, then `mise trust .`, then copies every `.env` file found in the source repo (root and any subdirectories, mirroring their relative paths via `mkdir -p`), then runs `lefthook install` if the freshly-cloned repo has a recognized Lefthook config (`lefthook`, `.lefthook`, or `.config/lefthook`, with a `yml`, `yaml`, `json`, `jsonc`, or `toml` extension) — so the user can watch progress. **New-tab placement** follows the gap: `side = "right"` places it immediately right of the sibling *below* the gap (the common case — e.g. `foo2` right of `foo1`), `side = "left"` places it immediately left of the lowest open sibling (when filling below the minimum — e.g. `foo1` left of `foo2`). The `.env` walk prunes `.git`, `node_modules`, `.venv`, `venv`, `__pycache__` **and every git-ignored directory** — a fixed name list alone let the walk descend into `.cache/`, where one repo's pytest tmpdirs contributed 102 throwaway `.env` files and their whole directory tree to the clone command. Only *directories* are tested against gitignore; `.env` itself is ignored in nearly every repo, which is precisely why it needs copying. `git check-ignore` is index-aware, so an ignored directory holding tracked files is still walked. The walk is breadth-first with **one `check-ignore` per depth level, not per directory** — git's startup cost dominates, and batching took a 206-directory repo from 2.2s to 0.2s. Both Lefthook paths self-gate on a config being present; existing checkouts additionally skip installation when `check-install` reports that their hooks are already current. Because targeting fills gaps in the *open* family (not a filesystem skip-existing scan), triggering repeatedly walks through the missing slots and then off the top; if the picked directory already exists on disk it's opened rather than cloned. Setup errors (not a git repo, no `origin` when cloning, name exists but isn't a directory, mkdir failure) abort with an `iterm2.Alert` before the tab is created; clone failures surface in the pane as git's own stderr. The RPC body is fire-and-forget — the real work runs as an `asyncio` task — because iTerm2's RPC dispatcher has a short timeout that the confirm dialog + clone easily exceed. The pure helpers (`select_sibling_slot`, `tab_title_for_destination`, `sibling_base`/`sibling_number`/`is_sibling`, `resolve_repo_root`, `resolve_origin_url`, `compute_destination`, `existing_checkout_update_command`) live in `iterm2/clone_repo_lib.py` and have `unittest` tests in `iterm2/test_clone_repo_lib.py` — run via `python3 iterm2/test_clone_repo_lib.py`.

`install.sh` also writes three iTerm2 `defaults` (default-profile GUID, 10% inactive-pane dimming, and `ShowSessionStatusInTabSubtitle` off so OSC 21337/7501 session status — Codex's "Working" — stays out of tab subtitles; the colored status dot has no setting and still shows) — but **only when iTerm2 is not running**. iTerm2 flushes its in-memory prefs to disk on quit and would clobber any `defaults write` made while it was open. If install reports `skip iTerm2 defaults`, quit iTerm2 and re-run `install.sh`. (The plist it clobbers is `com.googlecode.iterm2.plist`; the same rule applies to any hand/script edit of that file — do it only while iTerm2 is fully quit.)

**Restored windows use a frozen profile snapshot.** A restored pane/window keeps the profile settings that were live when its arrangement was saved — it does **not** re-read `dynamic-profile.json`. So a dynamic-profile change only affects sessions started *after* the change; a plain new tab heals only new panes, and "some panes behave differently after a profile edit" is expected. Worse, the `SaveWindowArrangement.py` daemon auto-saves titled windows on a debounce, so a *briefly*-toggled profile key gets baked into every saved arrangement inside `com.googlecode.iterm2.plist` and persists there long after the live profile is reverted — the daemon can re-pollute arrangements any time a polluted window is open when it next fires.

**Claude Code + scrollback:** CC repaints the entire alternate screen every frame instead of scrolling lines off the top, so iTerm2's `Scrollback in Alternate Screen` profile key is **inert for CC** — don't add it to `dynamic-profile.json` (it only lets the SaveWindowArrangement daemon re-pollute arrangements, pure downside). Native mouse-wheel scrollback for CC comes instead from `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` in Claude Code's own `settings.json` env (equivalent to `"tui": "default"`; lives in the aiconf config, outside this repo). That renders CC on the main screen so the terminal owns selection / `Cmd`-click URLs / real scrollback, at the cost of `Ctrl+O` transcript view and in-app mouse.
